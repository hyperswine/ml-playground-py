# Custom 557M model: M1 pilot

Date: 2026-10-19. Status: fixed 64-update learning pilot, final checkpoint audit and local evidence backup complete. This stage ran on the M1 only, as requested. No cloud resources were created. Model weights and optimizer progress remain on the M1.

## Scope and architecture

This begins a separate custom model lineage with random weights. It reuses the existing tokenizer and its fixed 65,536-token mapping, without loading teacher embeddings or any 168M model weights. A wider network cannot directly resume the existing narrower checkpoint.

The [architecture preset](../configs/qos_ai_557m.json) has 24 decoder blocks, embedding width 1,280, 20 attention heads, learned positions for a 512-token context, a 4x GELU feed-forward layer, and tied input/output embeddings. Counting the actual modules on PyTorch's meta device gives **556,526,080 unique parameters**. This preserves the current architecture family; architecture modernization and longer contexts are separate experiments.

The [separate runner](../src/ml_playground/training/qos_ai_scale.py) leaves existing training commands and models untouched. It supports AdamW, Adafactor and SGD; activation checkpointing; deterministic step-keyed training windows; complete optimizer-boundary recovery; restricted-reader checkpoints; finite-loss/gradient/weight checks; and atomic progress publication. Recovery binds architecture, vocabulary/data identity, source code, optimizer, schedule, seed, device and PyTorch version. A bounded segment resumes the same total schedule rather than starting another warmup.

## M1 memory choice

The verified host is `JQs-Mac-mini.local`, reached as `jq@100.107.153.43` over Tailscale. It has 16 GiB physical memory and PyTorch 2.13.0 with MPS.

FP32 parameter-state estimates, excluding activations, temporary tensors and allocator overhead:

| Optimizer | Weights + gradients + persistent optimizer state |
| --- | ---: |
| SGD without momentum | 4,452,208,640 bytes |
| AdamW | 8,904,417,280 bytes |
| Adafactor | 4,454,950,912 bytes |

The runner caps its MPS allocation budget at 6 GiB. It refuses this model's AdamW parameter-state floor under that budget. An initial SGD shape/recovery check runs two updates at sequence length 64. The learning pilot uses Adafactor and the full 512-token context.

Adafactor stores row/column second-moment factors for matrices rather than two dense Adam moment tensors. This changes the optimization method, so this pilot is not an Adam parity experiment. See the [original Adafactor paper](https://arxiv.org/abs/1804.04235). The installed PyTorch implementation uses parameter-relative updates and a relative-step cap; its learning-rate value must not be interpreted as an Adam learning rate.

## Fixed learning treatment

The Adafactor run uses seed 7, FP32, 64 optimizer updates, sequence length 512, microbatch 1, accumulation 1, learning-rate cap 0.01, 8-step warmup followed by cosine decay to 10% of the cap, weight decay 0.01, gradient clipping at norm 1, and per-block activation checkpointing. Total scheduled training exposure is **32,768 tokens**, sampled with replacement from the training stream. It is not a pass over all available data.

Two initial updates establish a saved boundary. Subsequent processes continue for at most 16 updates at a time, with saves every 8 updates and at segment ends. The per-process training-loop budget is 15 minutes. Each segment evaluates the same four 512-token internal-validation windows (2,048 target tokens). The treatment is fixed before continuing beyond update 2; it is not selected from development benchmark scores.

```sh
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 caffeinate -i .venv/bin/python -u qos_ai_scale.py train \
  --config qos_ai_557m.json --data curricula/scale_557m_20261019 \
  --output experiments/scale_557m_adafactor_20261019 \
  --device mps --optimizer adafactor --steps 64 --segment-steps 16 \
  --sequence-length 512 --batch-size 1 --grad-accumulation 1 \
  --learning-rate 0.01 --warmup-steps 8 --save-every 8 \
  --max-minutes 15 --checkpoint-blocks --resume
```

Use `--resume` only for an existing saved experiment. A new experiment omits it. The saved `progress.pt` contains weights, optimizer state, RNG state, accepted update history and frozen settings. Final `student.pt` uses the existing inference format. Checkpoints remain separate from the current default model.

## Validation and initial observations

Seven focused tests pass locally and on the M1. They cover exact model count/tied weights; activation checkpoint gradient parity; target-weighted accumulation; source/case separation and copied-text exclusion; uninterrupted versus restarted Adam training including moments/RNG/schedule; Adafactor factored-state recovery; and the complete runner/export/token-integrity path.

The full 557M SGD check saved update 1, restarted in a fresh process, completed update 2 and exported a checkpoint. The full-context Adafactor pilot completed its first two updates with finite loss/gradients/weights. Fixed internal-validation loss changed from **11.28236 to 10.42970**. These early updates took about 7.5 seconds each, excluding setup/validation/checkpoint overhead. This is learning and feasibility evidence, not an improvement over the pretrained 168M checkpoint.

## Completed results and recommendation

The fixed treatment completed all **64 accepted optimizer updates**, consuming **32,768 known training target tokens**. All five processes exited successfully. The final audit checked consecutive update identities, the original learning-rate schedule, token accounting, finite published weights, exact equality of every exported tensor with saved optimizer-boundary weights, tied embedding storage, and the unchanged benchmark hashes. Existing inference loading accepted the full 556,526,080-parameter artifact.

| Completed update | Fixed internal-validation loss |
| --- | ---: |
| 0 | 11.28236 |
| 2 | 10.42970 |
| 18 | 7.25995 |
| 34 | 6.12753 |
| 50 | 5.97716 |
| 64 | 5.81276 |

Reported segment time sums to **501.21 seconds** (8.35 minutes), or **65.38 training tokens/second**, including periodic saves and final validation within the timed segments. This excludes model construction, initial validation and final weight export. Individual updates normally take about 7.3 seconds. This is one short run, not a long-term thermal or reliability bound.

Actual persistent Adafactor state tensors occupy **2,743,056 bytes**. Post-segment MPS allocations were 2,228,846,592 bytes; driver allocations were about 3.38 GB after the first segment. Those are post-segment observations, not peak memory measurements. The allocator cap remained 6 GiB. A search of all retained run logs found no matches for the recorded Metal command-buffer, traceback, runtime error, out-of-memory, nonfinite or target-count-mismatch patterns. CPU restart tests prove exact weight/moment/schedule parity; MPS bitwise reproducibility was not separately established.

**The model is not yet useful for answers.** All three 32-token, greedy, unguarded smoke samples (`The purpose of a compiler is`, `What is Sol?`, and `Write a Sol function that adds two numbers.`) emitted 32 newlines and did not emit the end token. The [raw audit and samples](data/qos_ai_benchmark/evidence/scale_557m_20261019/reports/final_audit/audit.json) preserve this result. Falling next-token loss after a few updates can reflect learning frequent tokens; it does not establish reasoning or instruction following. No development capability score or parameter-scaling benefit is claimed.

This is a viable M1 training platform for further bounded experiments. The next useful stage is broader pretraining data and a chosen token/time budget before additional supervised teaching. At this measured throughput, one million tokens is approximately 4.25 training hours and ten million approximately 42.5 hours, excluding additional overhead and interruptions. More batching may improve throughput but has not been tested. Repeating this small domain corpus is not a substitute for broader data.

## What this can establish

This stage tests model construction, the M1 training path, optimizer-state recovery, bounded memory and early loss reduction. The dataset and exposure are far too small to establish a qualitative capability upgrade from scratch. There is no matched-compute 168M control, and the optimizer differs from previous fine-tunes. A useful next experiment needs substantially broader pretraining data and an explicit time budget informed by measured M1 throughput, followed by the verified curriculum and unchanged development benchmarks.
