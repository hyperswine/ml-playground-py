# Qwen3.5-4B on the round-4 data: pilot, full pass and M1 evaluation

Created: 2026-11-01T08:30:00+11:00 (Australia/Sydney). Kind: experiment report. Cloud compute: US$8.86.
Follows the [4B plan](2026-10-29-QWEN-4B-20USD-PLAN.md). Raw data: `data/qos_ai_benchmark/qwen4b_20261031/`
(scores, cost ledger, pilot training receipt). Answers and scores: `artifacts/qos_ai/mlx_4b_pilot_q8_20261031/`,
`artifacts/qos_ai/llama_4b_pilot_q8_20261031/` and `artifacts/qos_ai/mlx_4b_full_q8_20261031/`.

## Summary

- Full fine-tuning of Qwen3.5-4B on the same round-4 mixture as the 2B (92,314 examples, 2,885 updates of 32,
  seed 7) gave the best scores so far on the frozen Sol tests (346/360), strict traces (110/120), dev lexical
  (63/90) and the trace guard (24/24).
- It fails the plan's screening decision. It wrote 5/36 working programs on the coding check (gate: 21) and
  no complete repair (gate: at least one). **The 2B round-4 model stays the reference.**
- Its coding weakness matches the pilot's. The answers usually omit the input bindings the prompt supplies, so
  the programs do not run. That points to the training data rather than model size or compute (not yet
  checked against the mixture itself).
- On the M1 the q8 model needs 5.5 GB at peak and runs at about 10.6 tokens/s overall, which meets the plan's
  local-inference target narrowly.

Every run used the RTX PRO 6000 (96 GB, secure cloud, EU-RO-1, $2.49/hr). Training kept fp32 weights with bf16
autocast, AdamW at lr 1e-5 with a cosine schedule, and a 4,096/2,048 token/target budget per micro-batch. A full
pass took about 84 minutes at about 1.75 s per update (pilot: 1.85 s). Memory peaked at 74.6 GB allocated and 81.1 GB reserved.
The two full-pass attempts produced different weights (`65534641…` and `22fe0dbc…`). The order of examples was
the same, but GPU kernels are not bitwise deterministic.

### Why attempt 1 lost its weights

1. **The download broke.** `pod_pull.sh` opened 12 parallel SSH streams. Some were refused at connection time (likely sshd's
   default `MaxStartups` of 10) and some established streams were reset. The script waited on all streams
   without checking each one, so truncated pieces were joined. Its hash check caught the result twice.
2. **The backup copy did not fit.** `KEEP_ON_VOLUME=1` copies the weights to the volume when there is room.
   Inside the pod, `df` reports the shared MooseFS cluster (476 TB free), not the volume's 40 GB quota. The volume
   already held 37 GB, so the space check passed, the copy failed and the job removed the partial copy.
3. **The pod stopped before anyone noticed.** After a 25-minute pull wait the job stopped the pod, which wiped
   its container disk, the only copy.

Fixes, used for attempt 2:

- `pod_pull.sh` (on the M1) checks each piece's exact size and retries it up to six times, and uses at most 6
  streams. A test with a stand-in connection that cut pieces short at random still produced an identical file.
- `scripts/runpod/qwen_sft/job.sh` now waits for the pull until `HARD_CAP_MINUTES` whenever the weights are not
  also on the volume. `WAIT_MINUTES` only applies once a volume copy exists. A new `VOL_QUOTA_GB` makes the space
  check use the volume's quota.

Untuned 4B (llama.cpp q8_0 on the Windows PC) scored 1/48 complete, 11/36 programs and 0/24 on the guard. Its
740-prompt run was stopped partway, so it has no frozen-test scores. The pilot gave the same coding and guard
scores under llama.cpp on the PC as under MLX, and 335 frozen tests against MLX's 338.

The full pass improved on the pilot most in strict traces (+11), dev lexical (+8) and frozen tests (+8). It did
not fix code generation. Generate and repair stayed at 0/12, and stated outputs fell from 18 to 9.

## Decision and next step

Keep the 2B round-4 model as the reference. The 4B is better at Sol semantics and calculation but no better at
the coding task that motivated the experiment. More compute on the same data is unlikely to change that. The next
experiment should change the data: add training examples where the supplied input bindings are kept in the
program, and repairs that return a complete corrected program. Then re-check on the 2B first, which is cheaper.

About $6.80 of the $15.69 balance remains. The volume is 37/40 GB full, so a later 4B run should either keep
`KEEP_ON_VOLUME` off (now safe) or grow the volume first.
